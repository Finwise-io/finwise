What the map already shows

Shared UI is the heaviest thing in the app

93 files, more than any feature module, and it reaches into cash-flow, plan and net-worth directly — 94 imports across the three. A component that calculates is a calculation nobody will find. Splitting it is not part of this move, but it is the next thing worth doing after.

The layering is real, with one exception

Every feature module depends downward on the foundation, as it should. The exception is foundation → net-worth and foundation → cash-flow: the store reaches up into features. That is the one loop in the app, and the move is a good moment to break it.

The folder you asked for

One master folder, one folder per module, everything for that module inside it — the maths, the screens, the components and the tests together, so a module can be understood without hunting.

Imports become @net-worth/… rather than a trail of ../../, so a file can move within its module without touching anything else. The route files in app/ stay exactly where they are — they are one-line re-exports, and routing is decided by their path.

Keeping two older versions

Every change to a module writes the previous code to older-code-<date>. Two are kept; a third is deleted. That much is straightforward. One consequence is not, and it is the opposite of what you are trying to achieve.

Old code inside the source tree gets compiled, tested, and can be imported

The typechecker reads **/*.ts and the test runner reads **/__tests__/**. Left alone, every archived copy is type-checked and its tests run — so an old version failing would break the build, and worse, a file could quietly import the archived copy and nobody would notice. That is exactly the stale-code problem this structure exists to prevent, arriving through the back door.

So the archive is fenced off three ways: excluded from the typechecker, excluded from the test runner and the bundler, and a guard test that fails the build if any live file imports anything under an older-code- folder. Without all three, the archive is a liability rather than a record.

Worth knowing: git already keeps every version, forever

git log on any file shows every change with its date and reason, and any old version can be recovered. The archive folders are worth having because they are visible — you can open them without a command — but they are a convenience on top of the real history, not the history itself. Keeping only two is safe for that reason.

How the move happens without breaking the app

368 files. Moving them at once would break every import at once. One module at a time, with the whole suite green before the next begins.

  1. 01 Add a path alias per module, so imports stop depending on where a file physically sits. Nothing moves yet; the suite must stay green.
  2. 02 Set up the fences — typechecker, test runner and bundler all told to ignore older-code-, plus the guard test that fails if anything imports from one.
  3. 03 Move debt first. Four source files, four tests, few dependents — the smallest real module, so the machinery is proven on something recoverable.
  4. 04 Then goals, insights, performance, accounts — small and self-contained.
  5. 05 Then net-worth, cash-flow, plan — the heavy ones, each its own session.
  6. 06 Then setup, shared-ui and foundation last, because everything else depends on them and they should move when nothing is still in motion.
  7. 07 Delete src/ once it is empty, and regenerate this map from the new structure.

After each module: full suite, typecheck, and the map regenerated. If any step cannot be made green, that module goes back and the reason is written down before trying again.

The honest cost

Roughly four to five sessions, and it produces no new capability — nothing works that did not work before. What it buys is that every file for a module sits in one place, the archive makes the last two versions visible, and the guards make stale code fail loudly instead of running quietly.

The risk is real and worth stating plainly: this touches every file in the app. It is done one module at a time, behind a green suite, precisely because the failure mode is a broken build at the worst moment. If any module resists, it stops and you hear about it rather than being told afterwards.
